**Final result: PASSED**, after three rounds of fixes to `main`. Host `gpu-train-2`
(single NVIDIA L4, Python 3.10.12, pre-existing torch 2.9.1+cu129). The first

relaying instructions from a second Claude Code session (the one maintaining this

## What actually happened, in order

**Round 1 (failed at Step 2, install).** `requirements.txt`'s exact pins were
unresolvable on this machine: `torch==2.7.0+cu128` isn't on plain PyPI (needs
PyTorch's own index), and `numpy==2.4.4`/`pymatgen==2026.5.4`/
`pymatgen-core==2026.4.16` all require Python >=3.11 (this machine has 3.10.12).
Worked around by using the machine's preinstalled torch 2.9.1+cu129 and skipping
`mace-torch`/`e3nn` (not needed to train). Fix landed on `main`: every pin in
`requirements.txt` is now a floor (`>=`), not an exact version, split
`mace-torch`/`e3nn` into `requirements-eval-optional.txt`.

**Round 1 (failed at Step 4, training launch — `ModuleNotFoundError`).**
`scripts/train_arm.sh`'s `STEERING_PATH` resolution used string-prefix-stripping
(`${STEERING_PATH#../}`) instead of actually resolving the path, producing a
nonexistent location (`cues/steering/...` instead of the sibling directory
`steering` actually lives in). Separately, `ed_data.py` does a top-level
`from dielectric_data.reader import ...`, so `code/py/dielectric` (one level
below `code/py`) needs to be on `PYTHONPATH` too, not just `code/py`. Fix landed
on `main`: `STEERING_PATH` is now resolved by `cd`-ing to it and reading `pwd`
(works regardless of how many `../` it contains), and both path levels are
added to `PYTHONPATH`.

Also found in this round: `ed_train.py`'s own `--data`/`--checkpoint` plumbing
was fine, but a **git identity was not configured on this VM** at all (no
`user.name`/`user.email`), so even committing the report locally failed until
one was set for that single commit only (placeholder `.invalid` email, no
global config changed). A real external collaborator's own machine will
presumably already have their own identity configured, but this is worth
flagging explicitly in any future collaborator-facing doc.

**Round 2 (failed at Step 4 again — `--seed: unrecognized arguments`).** The
`steering` repo's vendored `ed_train.py` does not support `--seed` at all, even
though the main/private lineage does — the same kind of lineage drift the
design doc already documents for the qk-norm fix, just hitting a different flag
this time. Fix landed on `main`: `train_arm.sh` now probes
`ed_train.py --help` for `--seed` support and only passes the flag if present,
printing a loud warning and proceeding without seed control rather than
hard-failing.

**Round 3 — success.** With both fixes merged, `ed_lite` (238M params) trained
cleanly: `step 1/4000 ... loss 9.835` through `step 50/4000 ... loss 6.250`,
monotonically decreasing, finite throughout, then saved a real checkpoint —
`ed_lite_ckpt_000050.pt`, 3,809,288,735 bytes (~3.8GB; this includes optimizer
and EMA state, not just model weights, which is why it's larger than the
~900MB production inference checkpoint).

**Stopping the run surfaced one more real bug.** The documented stop command,
`pkill -f "ed_train.py.*--prefix ed_lite"`, is dangerous when run as a single
remote-exec string (`gcloud compute ssh --command "..."`, or any
`ssh host "..."`): the invoking process's own command line literally contains
the search pattern, so `pkill -f` matches and kills *that* process too — which,
for a single-command SSH invocation, took the whole SSH session down outright
(confirmed: this happened live during this test). Fixed by using the standard
bracket trick (`pkill -f "[e]d_train.py..."`), documented in `SETUP.md` along
with the more general gotcha (avoid the literal pattern anywhere else in the
same remote-exec string, including an `echo` fallback message — that self-matched
too on the first attempt at a "confirm it's stopped" check).

After stopping: `nvidia-smi --query-compute-apps` showed no processes (GPU
fully released), and the log had not advanced past step 50, confirming a clean
stop rather than a silent continuation.

## Open items, not resolved by this test

- **Corpus row count.** The design doc's original "~219k rows" figure doesn't
  match what's actually on HF (241,741 rows via `wc -l`, matching the HF
  dataset card's own stated 242,170). Corrected in `README.md` with a
  footnote — the ~219k figure was from an earlier/different-machine copy,
  before the version that was ultimately backed up to Hugging Face.
- **pymatgen's runtime necessity is still not fully confirmed.** `dielectric_data`
  (reached via `ed_data.py` at runtime, not at import time) uses pymatgen in
  `formatter.py`/`reader.py`/`validation.py`. The successful Round 3 run did
  exercise real data loading and did complete 50 steps without a pymatgen-related
  error, which is reasonably strong evidence pymatgen 2025.10.7 is fine for at
  least this arm's training path — but this wasn't specifically isolated as a test.
- **Disk headroom is tight on this VM** (5.6GB free after this test, down from
  9.6GB at the start) — a full matched retrain (3 arms × 2 seeds, each keeping
  up to 3 checkpoints at ~3.8GB each) will not fit here without active cleanup
  between runs. Worth flagging to any real external collaborator with a small
  disk.
- **Return-path for real external collaborators remains unresolved.** This VM
  has no git credentials configured at all, and pushing a branch to
  `rajkumars-work/cues` failed outright
  (`fatal: could not read Username for 'https://github.com'`). For this
  validation run, the fix was to relay the report back to the PI directly
  (this file). A real external collaborator — who in any case won't have push
  access to this repo — will need either their own fork + pull request, or
  the same relay-through-PI fallback. Neither is implemented as an actual
  documented option yet; that's the next thing to design before a real handoff.
- **`fetch_assets.sh`'s checkpoint-download path was not exercised** in this
  test (corpus-only fetch, to save disk/time) — only the dataset repo's HF
  access was confirmed, not the three checkpoint repos'.
- **Optional HF checkpoint upload was not attempted** this round (the real
  checkpoint now exists, but testing that path wasn't pursued given the core
  objectives were already met and disk/time were both already constrained).
